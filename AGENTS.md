# Frontend Development Guide

This directory is an independent Git repository containing the E-Matrix web
app. Its structure deliberately mirrors `tax-advice/web`.

## Stack

- Node.js `24`, Yarn 1
- Next.js 16 (App Router, Turbopack), React 19, TypeScript 6
- Tailwind CSS 4 with design tokens in `src/app/globals.css`
- TanStack Query hooks generated by Orval from the API's `swagger.json`
- react-hook-form + zod for forms
- next-intl for i18n (pt-BR, en, es)
- Biome for formatting and linting

## Commands

| Script | Purpose |
| --- | --- |
| `yarn dev` | Start the dev server on http://localhost:3000 |
| `yarn build` | Production build (also type-checks) |
| `yarn lint` | Biome check |
| `yarn typecheck` | `tsc --noEmit` |
| `yarn generate` | Regenerate `src/http/api.ts` from the API contract (`ORVAL_INPUT_URL`) |
| `yarn check:messages` | Fail when `en.json`/`es.json` keys differ from `pt-BR.json` |

`src/http/api.ts` is generated: never edit it by hand; it is excluded from
Biome. Requests go through `src/http/fetch-client.ts`, which injects the access
token, refreshes the session silently and retries once on 401.

## Internationalization

- The locale is **not** in the URL (unlike the legacy `/pt_BR/...` routes).
  `src/i18n/request.ts` reads the `NEXT_LOCALE` cookie, then the browser's
  `Accept-Language`, then falls back to `pt-BR`. `LanguageSwitcher` writes the
  cookie and refreshes the page.
- Catalogs live in `messages/`. `pt-BR.json` is the source of truth and types
  every `useTranslations` key (`src/global.d.ts`); keep `en.json` and
  `es.json` in sync and run `yarn check:messages`.
- Never hard-code user-facing text, including `aria-label`s, placeholders and
  zod messages (build schemas inside the component with `useMemo` and `t`).
- Format dates and numbers with next-intl's `useFormatter()`, not by hand.
- Calendar days without time (`YYYY-MM-DD`, e.g. period start and end) are
  shown with `useFormatDateOnly()` from `src/lib/format-date.ts`, which formats
  them in UTC. Never pass them to `new Date()` for display: that is midnight
  UTC, which renders as the previous day in UTC-3. Send them to the API as the
  `input type="date"` string, without converting.
- The API returns English error messages; `useTranslateError()` maps them to
  `errors.*` keys. When the API adds a message, add it to the map and to the
  three catalogs.
- Legacy translations (`ergomatrix/app/Resources/translations/*.yml`) are the
  reference for domain terms.

## Lists Sliced by Period

Records dated within a period (trainings, meetings and projects) are listed one period at a time. The slice is the
`period_id` parameter of the API, so changing it fetches again, while search,
sort and pages stay in the client. The filter lives in the URL as `?period=`
(a `ListStateConfig.filters` validator accepting a UUID or `all`) and its
default is resolved by the screen, not by the API: with no `period` in the
URL, `resolveDefaultPeriod()` in `src/lib/periods.ts` picks the period that
contains the user's local today (`toLocalCalendarDate()`), or else the one
with the greatest `end_date`, and writes it to the URL. `all` exists only in
the web URL and means omitting `period_id`. An unknown id, or a 404
`Period not found.`, reloads the periods once and applies the default again
instead of showing an error. `GET /periods` is readable by every role for
this reason. With no period registered, the screen lists everything and shows
a notice instead of the filter.

Build a sliced listing with the shared pieces in `src/components/list`, as
`treinamentos/page.tsx` does, instead of copying the logic:
`usePeriodSlice({ period, onPeriodChange, useRecords })` loads the periods,
resolves and writes the default, re-checks unknown or deleted periods once and
runs the module's records query (a module-scope hook taking `periodId` and the
query options); `PeriodFilter` (texts in the `periodFilter` namespace) renders
the select; `isPeriodFilterValue` is the `?period=` validator and
`ALL_PERIODS` the `all` value.

## Optional Modules

Avaliações is optional per installation and per type
(`ergonomic_analysis_in_loco`, `hit_list`, `checklist`, `change_assessment`,
the API's canonical order, the order of the legacy tabs), switched by
`EVALUATION_TYPES` in the API. The web never has a
`NEXT_PUBLIC_*` variable for it: it asks the API. `useEvaluationTypes()` in
`src/lib/evaluation-types.ts` reads `GET /evaluations/types`, cached for the
whole session (`staleTime: Infinity`), and `EVALUATION_TYPE_HREFS` maps each
type to its tab. The shells take their items from `useVisibleNavItems()`
(`components/shell/use-nav-items.ts`): an item with `requiresEvaluationTypes`
shows only when at least one type is enabled, and stays hidden while loading
and when the request fails, rather than offering a screen that would answer
404. A route of a disabled type calls `notFound()` before requesting its
listing. Changing `EVALUATION_TYPES` needs the API restarted, and the web
shows it only after the page is reloaded.

Every evaluation type runs on one generic core, driven by its **web
definition** (`avaliacoes/definitions/`, typed by
`EvaluationWebDefinition` in `definitions/types.ts`). A definition declares
the type, its tab (`EVALUATION_TYPE_HREFS`), the translated type and "Nova
…" labels, the row's name, the generated orval hooks adapted to common
signatures (listing, detail, activities, `POST`, `PUT`, `DELETE` and the
query keys), the form with its schema functions (`make…Schema`, default
values, `to…FormValues`, `to…Input`), the PDF adapter and the file base
name. `definitions/index.ts` holds the registry, which must cover every
`EvaluationType` (`satisfies`), and `evaluationWebDefinition(type)`.

What reads only the definition, and never names a type:

- `components/EvaluationTypePage.tsx` (one listing component, mounted with
  `key={type}`) and `components/use-delete-evaluation.ts`;
- `_form/CreateEvaluation.tsx`, `ViewEvaluation.tsx` and
  `EditEvaluation.tsx`: `EvaluationTypeGuard`, the skeleton, the load error,
  the Viewer sent back from the write routes, the success param
  (`?created=`/`?updated=<code>`) and the way back to the tab with its
  search, sort and page; the form is mounted with a `key` of the type (and
  the id), so no state survives a change of type or record;
- `_form/use-evaluation-activity-options.ts` and
  `components/use-evaluation-pdf.ts` (see PDFs).

The form and the report stay per type (D-6): each reproduces a legacy
layout. To add a type, after the API has its definition and routes:

1. `yarn generate`, so `src/http/api.ts` has its hooks, and add the type to
   `EVALUATION_TYPE_HREFS` in `src/lib/evaluation-types.ts`.
2. The form, `_form/<Type>Form.tsx`, over `form-parts.tsx` and
   `useGuardedSubmit`, taking the props of `EvaluationFormProps`.
3. Its schema functions in `_form/schema.ts`: the zod schema mirroring the
   API rules, the empty values, the stored record as form values and the
   request body.
4. The report module in `src/lib/pdf/<type>-pdf.ts` and its adapter,
   `definitions/<type>-pdf-adapter.ts`.
5. The definition, `definitions/<type>.ts`, added to the registry in
   `definitions/index.ts`.
6. The translations in `pt-BR.json`, `en.json` and `es.json` (the type, "Nova
   …", the form and the PDF), checked by `yarn check:messages`.
7. Four route files, each only passing the type: `<tab>/page.tsx`
   (`EvaluationTypePage`), `<tab>/novo/page.tsx` (`CreateEvaluationPage`),
   `<tab>/[id]/page.tsx` (`ViewEvaluationPage`) and
   `<tab>/[id]/editar/page.tsx` (`EditEvaluationPage`).

Nothing else changes: the listing, the deletion, the PDF hook and the three
pages take the new definition as they are.

The two Coletas de Dados In Loco are told apart by a suffix in every text
(tabs, titles, "Nova …", PDFs and errors): `ergonomic_analysis_in_loco` (CDIP,
`coleta-de-dados-producao/`) is "Coleta de Dados In Loco — Produção" and
`checklist` (CDIA, `coleta-de-dados/`) "Coleta de Dados In Loco —
Escritório"; keys, URLs and file names do not carry the suffix. The CDIP is
the first type to use two capabilities of the core:

- **A numeric answer** (`number` in the API catalog): question 5,
  `timesPerShift`, is a JSON number of at least zero or `null`. The form
  holds it as typed, in a one-line input with `inputMode="decimal"`;
  `parseLocaleDecimal` in `_form/schema.ts` reads it in the user's locale
  (a comma or a point as the decimal separator, "1.000" a thousand in pt-BR
  and es), and the zod schema, built with the locale, turns it into the
  number the body sends. The stored number comes back written with
  `useFormatter().number`, in the form and in the PDF.
- **The activity's location in the detail** (`detailActivityLocation` in the
  API definition): the detail's `activity` also has its current `area` and
  `fabric` (`EvaluationActivityLocation`), the listing never. The form keeps
  them in `location`, shows them only in the view, read only, and never sends
  them.

Its rows show the `sector` in the name column (it has no name of its own).

## Access Roles

`useAuth()` exposes `isAdmin` (users, parameters) and `canEdit` (admin or
user; viewers only read). Hide what a role cannot do, but remember the API is
the real guard.

## Theming and the Two Layouts

Components only use token classes (`bg-primary`, `text-on-surface`,
`bg-ematrix-dark`...). The palette follows the legacy E-Matrix colors.

There are two layouts, chosen by each user in `LayoutSwitcher` (next to the
`LanguageSwitcher`):

- **Modern** (`modern`), the default: the tokens of `@theme` in
  `globals.css`, with no attribute on `<html>`.
- **Classic** (`classic`): the legacy look (Bootstrap 3 + Bootswatch Paper,
  Roboto, 3px corners, Paper shadows). The block `[data-layout="classic"]` in
  `globals.css` overrides the tokens, outside `@layer theme` so it beats
  Tailwind's `:root`. Shadows (and the bare `rounded`) are written into the
  utilities by Tailwind 4, so the same file overrides their `--tw-shadow`
  in `@layer utilities`. The chart colors (`--color-chart-*`) never change.

The choice lives in the `EMATRIX_LAYOUT` cookie (`modern`|`classic`, any
other value is `modern`; `path=/`, `sameSite=lax`, 365 days), next to
`EMATRIX_SIDEBAR` (`collapsed`|`expanded`) for the classic sidebar.
`src/lib/layout-preference.ts` holds the names, the parsers and the client
writes, without React. The root layout reads both cookies with `cookies()`,
renders `<html data-layout="classic">` only for the classic layout (so the
first frame never flashes the other one) and hands the values to
`LayoutPreferenceProvider` (`useLayoutPreference()`: `layout`, `setLayout`,
`isSidebarCollapsed`, `setSidebarCollapsed`). `setLayout` writes the cookie
and the attribute in place, **without** `router.refresh()`, so the open
screen keeps its filters, modals and forms. Signing out keeps the cookies.

Roboto and Alfa Slab One (`--font-roboto`, `--font-alfa-slab`, the brand
font `--font-brand` in the classic block) come from `next/font/google` with
`preload: false`, so the modern layout never downloads them.

The `classic:` variant (`@custom-variant classic`) styles what a token cannot
express. Only `src/components/ui`, `src/components/auth`,
`src/components/shell` and `src/app/login/page.tsx` may use it or read the
layout; pages change only through the tokens and the primitives, never in
two versions. A component that only uses token classes gets the classic
layout for free. Where the shell needs another structure, `(app)/layout.tsx`
swaps it: `ModernShell` or `ClassicShell`, always as a sibling of the same
`ShellContent`, so the page stays mounted.

The classic sidebar's "Menu" button calls `setSidebarCollapsed`, which writes
`EMATRIX_SIDEBAR`; the root layout reads it, so the sidebar already renders
at 60px when collapsed (wide screens only; below `lg` it is the drawer). A
page element fixed beside the sidebar reads its width from
`--shell-sidebar-width` (the classic `<main>` sets 265px or 60px; unset, it
is the modern 16rem), as the fixed form footers do with
`lg:w-[calc(100%-var(--shell-sidebar-width,16rem))]`. The
classic header gradient lives in `headerClasses` of `classic-shell.tsx`, and
the background image in the `classic-background` utility of `globals.css`,
rendered only by classic elements (the access screens use
`classic:classic-background`) so the modern layout never downloads
`public/classic/*`. The access screens (login, `AuthCard`) show the
`LayoutSwitcher` in both layouts; in the classic one they are a single white
panel with the round logo (`ClassicLogo`, a CSS background, never an `<img>`)
and `Copyright` shows the legacy footer text.

## PDFs

Legacy PDF reports (wkhtmltopdf) are rebuilt in the browser with `jspdf` and
`jspdf-autotable`, pinned to exact versions in `package.json`. Reports live in
`src/lib/pdf`, without React: the screen passes the translated labels and the
already formatted values (dates with `useFormatDateOnly()`), and the module
returns a `Blob` that the screen saves with `saveBlobAsFile`. Load them with
`import()` only when the user asks for a PDF, so `jspdf` stays in its own
chunk, out of the bundle of the screens. Use the standard Helvetica (WinAnsi):
it covers the accents of pt-BR and es, but not characters outside cp1252.

- `load-photo.ts`: turns an attachment `Blob` into a JPEG for the PDF, with
  the EXIF orientation applied and the longest side at most 2,000 px, or
  marks it unavailable when it does not decode. Use it for any photo that
  goes into a report.

`projetos/components/use-improvement-project-pdf.ts` is the screen side:
it downloads the photos, generates one PDF at a time and reports a failure
with `projects.pdf.error`. For the evaluations, one hook serves every type:
`avaliacoes/components/use-evaluation-pdf.ts` takes the type's definition,
fetches the detail on the click (`GET /evaluations/<segment>/{id}`, nothing
for the blank form) while the adapter loads the report, saves
`toExportFileName(code, <file base name>, 'pdf')` or `<file base name>.pdf`,
keeps one PDF at a time and reports a failure with `evaluations.pdf.error`.
The adapter of each type, `avaliacoes/definitions/<type>-pdf-adapter.ts`,
reads the translations and formatters it needs and imports its module of
`src/lib/pdf` on demand:

- `hit-list-pdf-adapter.ts` turns the answers into the report's texts (an
  empty or mistyped answer is blank, a yes/no not answered marks neither)
  and loads the 14 images through `loadPdfPhoto`; saved as
  `HL-<n>-hit-list.pdf` or `hit-list.pdf`.
- `checklist-pdf-adapter.ts` does the same for the Coleta de Dados. The 11
  blocks and the questions whose expected answer is "no", which give the
  points of each option, live in `avaliacoes/components/checklist-blocks.ts`,
  the web's only copy, shared by the PDF and `ChecklistForm` (D-3). Its
  `computeChecklistScore` repeats the API's `presentChecklistScore` (same
  rule, same two-decimal rounding, `null` without any answer) only for the
  live score of the form; the PDF's sums and percentages still come from the
  API `score`, the percentages formatted with `useFormatter().number` (at
  most two decimals, then `%`: `96,36%` in pt-BR and es, `96.36%` in en;
  `null` is blank). Saved as `CDIA-<n>-coleta-de-dados.pdf` or
  `coleta-de-dados.pdf`.
- `change-assessment-pdf-adapter.ts` does the same for the AMP: the date
  formatted with `useFormatDateOnly()`, an empty answer blank, saved as
  `AMP-<n>-avaliacao-de-mudancas.pdf` or `avaliacao-de-mudancas.pdf`. The 8
  question keys, in the legacy order, live in
  `avaliacoes/components/change-assessment-questions.ts`, the web's only
  list, for the PDF and the form.
- `ergonomic-analysis-in-loco-pdf-adapter.ts` does the same for the CDIP:
  the date with `useFormatDateOnly()`, question 5 with
  `useFormatter().number` (`2,5` in pt-BR and es, `2.5` in en), the activity
  as `código — nome` and the area and fabric of the detail; saved as
  `CDIP-<n>-coleta-de-dados-producao.pdf` or `coleta-de-dados-producao.pdf`.
  The 20 question keys and the 5 steps of question 8, in the legacy order,
  live in `avaliacoes/components/ergonomic-analysis-in-loco-questions.ts`.

## Exports

Tables are exported in the browser, from the rows the screen already holds,
never by the API. Exporters live in `src/lib/export`, without React, like
the PDFs: the screen passes an `ExportTable` (`table.ts`) with the
translated column labels and the values already formatted for display
(`null` is an empty cell), and the module returns a `Blob` that the screen
saves with `saveBlobAsFile`. Name the file with `toExportFileName()`, which
turns the characters invalid in file names into `-`.

- `csv.ts` (no dependency): `;` as the separator (the legacy one, which
  Excel in pt-BR splits on), UTF-8 with a BOM, CRLF and RFC 4180 quotes. A
  value starting with `=`, `+`, `-`, `@`, tab or CR gets a `'` in front, so
  spreadsheets do not run it as a formula.
- `xlsx.ts`: one sheet, every cell of type string, no formatting. It loads
  `write-excel-file` (pinned to an exact version in `package.json`) with
  `import()`, and the screen loads the module with `import()` too, so the
  library stays in its own chunk, downloaded only when the user asks for
  Excel. Keep the library behind this module, so replacing it is a local
  change.

`matriz/components/use-matrix-export.ts` is the screen side: it exports the
visible columns, in the order of the screen, and every row that passes the
search and the filters, of every page, as `matriz-<period>.csv|.xlsx`, one
file at a time, and reports a failure with `matrix.export.error`.
